What this teaches

Simple to start. Harder to scale.

Suppose you create a simple server and host it on the internet.

A client can interact with your service using its hostname or IP address, and the incoming requests are handled directly by your server.

This is a simple and fast setup, but it puts more responsibility on the server. Along with your application’s business logic, the server may also handle tasks such as:

  • SSL/TLS terminationThe server completes the HTTPS handshake and turns encrypted traffic into a request the application can process.
  • Encryption and decryptionData is converted between readable form and a protected form while it travels across the network.
  • Compression and decompressionPayloads are made smaller before transfer and expanded again when received.
  • Connection handlingThe server opens, maintains, reuses, and closes network connections from clients.

For low traffic, this usually isn't a problem. Even a standard server can comfortably handle hundreds of requests depending on the workload.

So while this setup works well for small applications, it becomes harder to scale and maintain as traffic grows.

What this gives us

  • Simple request path
  • Minimal infrastructure
  • Easy local development
  • Low operational cost

What becomes a problem

  • Single point of failure
  • Limited capacity
  • No automatic failover
  • Client knows the server address
  • Scaling exposes more server addresses

The design pressure

What should we improve first?

The application server should not need to expose its address or handle every infrastructure concern itself.
