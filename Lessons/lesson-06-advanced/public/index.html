What this teaches

Remove the single gateway bottleneck.

Once the API Gateway becomes the main entry point, it can itself become a Single Point of Failure (SPOF).

To avoid this, we can run multiple API Gateway instances and place another load balancer in front of them.

The flow becomes:

Client→Edge / L4 Load Balancer→API Gateway Instances→Services

This outer load balancer distributes incoming connections across the available API Gateway instances.

It is often a Layer 4 load balancer when its main responsibility is simply to distribute traffic using IP addresses and ports rather than inspect application-level requests.

It may also be called an edge load balancer because it sits near the outermost entry point of the infrastructure.

This gives us:

  • High availability: More than one API Gateway can accept traffic.
  • No single API Gateway SPOF: Another healthy gateway can receive new connections if one fails.
  • Horizontal scaling: More API Gateway instances can be added as traffic grows.
  • Higher traffic capacity: Incoming connections are spread across the gateway tier.

Responsibilities are now separated:

Edge / L4 Load BalancerDistributes connections across API Gateway instances.
API GatewayUnderstands API requests and routes each one to the appropriate service.
Internal L7 Load BalancerDistributes service traffic across instances of a particular service.

In our setup

An Nginx stream proxy acts as the Edge/L4 Load Balancer and distributes TCP connections across two identical API Gateway instances. It does not inspect the HTTP path.

The selected API Gateway reads the path and routes User and Order requests directly. Product requests continue to an internal L7 Catalog Load Balancer, which selects one of two Catalog Service instances.
