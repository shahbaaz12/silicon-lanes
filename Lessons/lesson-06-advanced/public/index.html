What this teaches

Remove the single API Gateway SPOF.

Once the API Gateway becomes the main entry point, it can become a Single Point of Failure (SPOF). To avoid this, we run multiple API Gateway instances and place another Load Balancer in front of them.

Client→Edge/L4 Load Balancer→API Gateway Instances→Services

The outer Load Balancer distributes incoming connections across available API Gateway instances. It can operate at Layer 4 because its main responsibility is to use transport information such as IP addresses and ports, rather than inspect application-level paths.

It is also called an Edge Load Balancer because it sits near the outermost entry point of the infrastructure.

High availability

More than one API Gateway can accept traffic.

No gateway-instance SPOF

Another healthy gateway can receive new connections if one fails.

Horizontal scaling

More gateway instances can be added as traffic grows.

In our setup

Nginx performs three distinct infrastructure jobs.

An Nginx stream proxy acts as the Edge/L4 Load Balancer and distributes TCP connections across two identical API Gateway instances. The selected gateway reads the path and routes User and Order directly. Products continue to an internal L7 Catalog Load Balancer, which selects one of two Catalog Service instances.

What this gives us

  • No single API Gateway instance SPOF
  • Horizontally scalable gateway tier
  • Higher public-entry capacity
  • Clear separation of L4 and L7 decisions
  • Selective Catalog scaling remains intact

What still remains

  • The single Edge Load Balancer is now the outermost SPOF
  • Gateway configurations must remain consistent
  • The internal Catalog Load Balancer is one instance
  • Every cacheable request still reaches the backend
