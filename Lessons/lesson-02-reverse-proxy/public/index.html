What this teaches

Add a reverse proxy in front of the service.

The next logical and meaningful improvement is to add a reverse proxy.

A reverse proxy is a server that sits in front of your application server. Clients send requests to the reverse proxy, and it forwards those requests to the appropriate backend server.

It can also take over several request-related responsibilities, such as:

  • SSL/TLS termination
  • Encryption and decryption
  • Compression and decompression
  • Connection handling

A reverse proxy can also be configured to cache certain responses. If the same request comes again, it can serve the cached response directly without reaching the application server.

Origin shielding is another advantage: clients see only the reverse proxy address, while the original application server URL remains hidden. When direct access to the backend is blocked, this reduces its public exposure and adds a layer of anonymity and security.

This reduces the load on the backend server and allows it to focus more on business logic.

So the flow becomes:

Client→Reverse Proxy→Application Server

In our setup

We use Nginx as the reverse proxy.

The first request is a MISS, so Nginx forwards it to the Catalog Service and stores the response for 15 seconds. A repeat request is a HIT: the proxy responds without waking the application server. After the TTL, Nginx reports EXPIRED and refreshes upstream; after Clear cache, the next request is a fresh MISS.
