What this teaches

Cache responses closer to the client.

This is a good point to introduce a CDN (Content Delivery Network) and caching.

The CDN sits closer to the client and can cache frequently requested content.

The flow becomes:

Client→CDN→Edge Load Balancer→API Gateway→Services

If the requested content is already cached at the CDN, it can be returned directly to the client:

Client→CDN Cache→Response

The request never reaches the backend infrastructure.

If the content is not available in the cache—a cache miss—the CDN forwards the request to the infrastructure:

Client→CDN→Edge Load Balancer→API Gateway→Service

The response can then be cached by the CDN so future requests for the same content can be served directly.

This helps:

  • Reduce traffic reaching the servers.
  • Reduce backend load.
  • Improve response time.
  • Serve users from geographically closer locations.

CDNs are especially useful for static or cacheable content such as images, videos, CSS, JavaScript files, and selected API responses.

Note: real systems usually have several load balancers

A CDN does not discover the destination automatically. Its distribution is configured with an origin hostname or an origin group.

Cache behaviors can map request paths to the desired origin. DNS, Anycast, or a global traffic manager can then resolve that origin hostname to the appropriate regional or edge load balancer. From there, internal load balancers continue routing traffic to the correct gateway and service instances.

Origin groups can also define a primary and secondary origin so the CDN can fail over when the primary origin is unavailable.

In our setup

The Local CDN has one configured origin: advancedEdgeLoadBalancer1:80. On a cache miss or bypass, it forwards the request to that Edge/L4 Load Balancer.

Only GET /api/products is cached for 15 seconds. A Product MISS reaches the origin and stores the response; a Product HIT returns immediately. User and Order requests show BYPASS and continue to the origin.
