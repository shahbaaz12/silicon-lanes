How did your request even find Silicon Lanes?

Every lesson so far started the moment a request arrived at one of our containers. This one rewinds further back, onto the open internet, and answers a question the other lessons quietly skip: when you type a web address, how does your computer end up talking to one specific machine — possibly one of hundreds, possibly on another continent?

No Docker here. Just an explanation, built from the ground up. If a word shows up in this lesson, it gets explained before it's used.

IP addresses DNS Anycast BGP routing

Start here

Four words, in plain English.

Everything in this lesson is built out of these four ideas. Nothing fancy yet.

IP address

A number that identifies a machine on a network, like 203.0.113.10. If you want to send data to a computer, this is what you actually need. Names don't work at this level — only numbers.

Domain name

The human-friendly name, like yourapp.com. Easy to remember, completely useless to the network on its own. It has to be turned into an IP address first.

DNS

The system that turns a domain name into an IP address. Think of it as the internet's phone book: you look up a name, you get back a number.

Resolver

The helper that does the phone-book lookup on your behalf — usually run by your internet provider, or a public one like 8.8.8.8. Your browser asks it, it asks around, it comes back with an answer.

The normal case

One name, one address, one server.

Before anything clever happens, here's the setup most applications actually run. It's worth seeing plainly, because the fancy version is just a variation on it.

Your browserwants yourapp.com
→
DNS“that's 203.0.113.10”
→
One serverin one building, London

You ask for a name, DNS hands back one number, your computer connects to the one machine that has that number. Clean and simple, and genuinely how a huge number of real applications work today.

The catch shows up when your users aren't all in London. Someone in Sydney is now sending every request roughly seventeen thousand kilometres and back. Nothing is broken — it's just slow, and no amount of tuning that London server fixes it. The problem isn't the server. It's the distance.

So the question becomes: how do we put copies of this thing all over the world, without making users memorise a different address for each one?

Two ways to solve it

Give different answers, or give one answer that means different things.

There are two genuinely different strategies here, and mixing them up is the single most common source of confusion in this topic.

Approach 1

GeoDNS — hand out different addresses

Each location gets its very own IP address. When someone in Sydney asks DNS for yourapp.com, DNS looks at roughly where the question came from and replies with the Sydney address. Someone in London asks the same question and gets the London address.

The decision is made by DNS, at lookup time. Different people genuinely get different numbers.

Approach 2

Anycast — hand out one address everywhere

Every location shares the exact same IP address. DNS gives that one number to everybody on the planet, no matter who's asking. It has no idea where you are and doesn't try to find out.

The decision is made by the network itself, after DNS is already finished, as your data physically travels.

Both are real, both are widely used, and plenty of large providers use a mix. But it's the second one that makes people stop and squint — because on first hearing, it sounds like it shouldn't be legal, let alone functional.

The obvious objection

Hold on. The same IP address in multiple places? Isn't that a conflict?

This is the right thing to get stuck on, and it usually comes bundled with a second worry: surely DNS notices? Surely something rejects it when you try to register it? Here's the honest answer, in three parts.

1

DNS never checks. It's a text field, not a verification system.

This is the part that surprises people most. When you point a domain at an IP address, you're filling in a record — and DNS stores exactly what you typed. It does not ping the address. It does not look up who owns it. It does not know or care what country it's in, whether it's live, or how many machines answer to it.

You could point your domain at an IP address belonging to a company on the other side of the world right now, and DNS would store it without complaint. It simply wouldn't be useful — visitors would be sent to a machine that has no idea who you are. But nothing would reject it.

So there's no "registration conflict," because there was never a registration step that looks at location. DNS is a lookup table, and you own the row.

2

The network was already built to handle multiple paths.

Here's the piece that makes anycast click. Internet routing doesn't work on single addresses — it works on ranges. Instead of a route to 203.0.113.10, routers keep a route to a whole block like 203.0.113.0/24 (that notation just means "these 256 addresses, as one unit"). A range like this is called a prefix.

Now: routers have always had to cope with knowing several different paths to the same prefix. That's completely ordinary — the internet has redundant links everywhere, and picking between them is a router's day job. It's not an error condition. It's the normal state of affairs.

Anycast doesn't sneak past this. It just deliberately uses the behaviour that was already there: announce the same prefix from many places, and let every router do what it already does — pick whichever path looks cheapest from where it's standing.

3

The real guardrail is ownership, and it lives in routing, not DNS.

If DNS doesn't check, what stops anyone announcing any address? Ownership does — enforced one layer down.

IP address blocks are allocated by regional registries (ARIN, RIPE, APNIC and their siblings). To announce a block to the internet you also need to be an Autonomous System — one independently-run network, like an ISP or a cloud provider, with its own registered number. Networks increasingly publish cryptographically signed records saying which Autonomous System is permitted to announce which prefix, so their neighbours can reject announcements that don't match.

Announcing a prefix you don't own is a genuine attack, called BGP hijacking, and it has happened at real scale more than once. The defence lives here, in routing — not in DNS, which was never looking.

Your second question

So is an anycast address a “virtual IP”?

Sort of — but that phrase usually means something narrower, and the difference matters. There are three distinct things people call "an IP address," and they behave very differently.

Ordinary (unicast)

203.0.113.10
London

One address, one machine. The everyday case. This is what almost everything you've ever set up uses.

Virtual IP (VIP)

203.0.113.10
Server AServer B

One address that isn't nailed to one machine — but only ever one machine holds it at a time. If A dies, B takes the address over. Same building, same network. This is a failover trick.

Anycast

203.0.113.10
MumbaiFrankfurtVirginia

One address, many machines, all live simultaneously — in different cities, on different continents. Nobody is on standby. Routing decides who you reach.

So: yes, an anycast address is "virtual" in the loose sense that it isn't tied to one physical machine. But when someone says virtual IP in a normal infrastructure conversation, they almost always mean the middle card — a failover address inside one data centre, where exactly one machine is live at a time. Anycast is the third card, and it's a different mechanism at a different layer solving a different problem.

Worth noticing: the middle and right cards solve different problems. A VIP is about surviving a dead machine. Anycast is about being physically closer to your users. You can absolutely have both at once.

Your third question

Do real applications have just one IP address?

Often, yes — and that's completely fine. The answer depends on scale, and most teams never touch anycast directly at all.

Most applications

One address, one region. No anycast anywhere.

A single load balancer sitting in one cloud region, with one public IP pointing at it. Users everywhere connect to that one place. This covers an enormous share of real production software, including plenty of things you use daily. It is not a design failure — it's the right call until latency actually becomes a problem worth paying to solve.

Most that need global speed

They rent someone else's anycast, by putting a CDN in front.

This is the key practical insight. When a team puts a CDN in front of their application, they point their domain at the CDN's addresses — and those are the anycast ones, already announced from that provider's locations worldwide. The team configures a hostname in a dashboard. They never own an address block, never run a router, never speak BGP.

So the honest answer to "how does an enterprise configure one IP in many locations?" is usually: they don't. Their CDN provider already did, and they're pointing at it.

The giants

They own the address blocks and run the anycast themselves.

The CDN providers themselves, the big search and cloud companies, the public DNS services. They hold their own allocations, operate their own Autonomous Systems, and announce their prefixes from their own locations globally. This is a small club, and it's a serious operational commitment.

Putting the pieces together

One address block, announced from three cities at once.

Here's the whole anycast idea in one picture, now that the parts have names.

Someone in Bengaluru asks DNS → gets 203.0.113.10
Someone in Berlin asks DNS → gets 203.0.113.10
Mumbaiannounces 203.0.113.0/24
Frankfurtannounces 203.0.113.0/24
Virginiaannounces 203.0.113.0/24
Identical address, identical announcement, all three live at the same time. DNS gave both people the same answer — the network is what sends them to different buildings.

Each of those three locations is called a Point of Presence, or PoP — just a physical site where a provider accepts connections from the public. A big CDN runs hundreds of them.

The system the routers use to spread and compare those announcements is BGP, the Border Gateway Protocol. It works a lot like directions passed between neighbours: every network tells the networks next to it which address ranges it can reach, those neighbours pass the message along and add their own name to the trail, and eventually everyone holds a table full of routes like "to reach 203.0.113.0/24, go via this network, then that one, then that one." When several trails lead to the same range, each router picks the one that crosses the fewest networks.

One honest wrinkle

BGP isn't looking at a map. It counts networks crossed, not kilometres travelled — and those two usually agree, but not always. Which is why anycast occasionally lands someone in a city that isn't the closest one on a globe. It picked the shortest network path, and network cables don't run in straight lines.

Bringing it home

Where this meets what you already built.

Everything in this lesson happens before Lesson 7's first line of code runs. DNS, anycast, BGP — that whole first half decides which CDN location a person reaches. From the moment their connection lands there, it's the story you already know: check the cache, and on a miss, forward to the origin — the Edge Load Balancer, the API Gateways, the Catalog Load Balancer, the replicas.

Running locally, all of that collapses to 127.0.0.1. There's one machine, no cities to choose between, and no BGP in sight. But the shape is identical, and every decision still gets made — just by Nginx on your laptop instead of by routers spread across the planet. That's the whole point: the same job, at wildly different scales.
