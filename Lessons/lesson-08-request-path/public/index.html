Your browser knows a name, not an address.

It knows yourapp.com. It has no idea what IP address that is, or which of the (possibly many) computers behind it should answer. That's the very first thing that has to be resolved, before a single packet aimed at your application goes anywhere.

Why BGP matters

The same IP address can legitimately live in three places at once.

This is the part that trips people up, so it's worth sitting with: anycast isn't DNS quietly picking a nearby server for you. The exact same IP address is broadcast from multiple physical locations at the same time. Every one of them is telling the internet "route traffic for this address to me." Nothing about the address itself says which one is closest — that's decided entirely by how your packet gets routed once it leaves your device.

All three PoPs announce the identical address. BGP — not DNS — decides which one each client actually reaches.

Most of the time this lines up with intuition: the client in Bengaluru lands in Mumbai, the client in Berlin lands in Frankfurt. But BGP isn't optimizing for the map — it's optimizing for network cost, usually the fewest networks a packet has to cross. Those two things are correlated, not identical, which is why anycast occasionally sends someone to a location that doesn't look like the nearest one if you're just eyeballing a globe.

A useful way to picture it

BGP works like directions passed between neighbors.

Every network (an Autonomous System, or AS) tells its neighboring networks which addresses it can reach. Those neighbors pass the announcement further along, tacking their own name onto the path as it travels. Eventually every network on the internet ends up with a table full of entries like "to reach this address, go via AS64500 → AS7018 → AS13335." When more than one path exists to the same address — exactly what anycast creates — each router just picks whichever path has the fewest networks to cross.

DNS, anycast, and load balancing keep getting mixed up. Here's the actual split:

Mechanism Who actually picks the target Layer
Anycast BGP routers, from network topology L3 · Network
Round-robin DNS / GeoDNS The DNS server, per query DNS protocol
Load balancer The load balancer, per connection or request L4 or L7

Under anycast, DNS isn't load balancing anything — it hands back the same answer to everyone, every time. The distribution effect comes entirely from BGP, underneath that one shared address. DNS only starts actively spreading clients across different addresses when it's doing round-robin or GeoDNS instead, which hand back different answers to different callers.

Back to Silicon Lanes

Lesson 7's CDN is where this diagram rejoins ours.

In a real deployment, the moment a client's packet lands at a CDN PoP is the moment Lesson 7 picks up the story. Everything before that — DNS, anycast, BGP — decided which PoP; everything after it is the cache, the Edge Load Balancer, the API Gateways, and the L7 Catalog Load Balancer you already built by hand across Lessons 6 and 7. Locally, all of that collapses to 127.0.0.1, because there's only one machine and no BGP to speak of — but the shape of the chain is exactly the same.

Terms worth keeping straight

Anycast
The same IP address, announced from multiple physical locations at once. BGP decides which location a given client actually reaches.
BGP
Border Gateway Protocol — the way independent networks (Autonomous Systems) tell each other which addresses they can reach, and how routers pick a path when several exist.
Autonomous System (AS)
One independent network on the internet — an ISP, a cloud provider, a CDN — identified by an AS number.
Point of Presence (PoP)
One physical location where a CDN accepts client connections. A CDN using anycast runs many of these behind one address.
GeoDNS
A DNS technique that returns a different IP depending on the resolver's location. Unlike anycast, the decision is made by DNS itself, not by routers.
