What this teaches

Scale only the services that need it.

We can use the API Gateway as the main entry point for all client requests.

Not every service needs a load balancer. We can place load balancers only in front of services that receive high traffic or need multiple instances.

For example:

Client→API Gateway→User Service
Client→API Gateway→Load Balancer→Order Service Instances
For HTTPS traffic

The TLS connection can terminate at the API Gateway. The gateway handles SSL/TLS work such as encryption and decryption before forwarding the request over the internal network.

This gives us a cleaner architecture:

  • API Gateway: Handles the external entry point, routing, authentication, rate limiting, TLS termination, and other shared policies.
  • Load Balancer: Is added only where horizontal scaling or high availability is needed.
  • Application services: Can focus mainly on business logic.

This also avoids adding unnecessary load balancers in front of services that do not need them.

A new single point of failure

A single API Gateway may now become the system’s Single Point of Failure (SPOF). If it goes down, clients cannot reach any service through the public entry point. The next improvement is to run multiple API Gateway instances behind another load balancer.

In our setup

The API Gateway routes User and Order requests directly to one service instance each. Product requests go through an L7 Catalog Load Balancer, which distributes them across two Catalog Service instances.

The local lesson uses HTTP, so it demonstrates routing and selective load balancing without configuring a TLS certificate.
