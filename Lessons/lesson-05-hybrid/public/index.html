What this teaches

Scale only the services that need it.

We can use the API Gateway as the main entry point for all client requests. Not every service needs a Load Balancer, so we add one only in front of a service that receives high traffic or needs multiple instances.

Client→API Gateway→User Service
Client→API Gateway→L7 Load Balancer→Catalog Replicas

For HTTPS traffic

TLS can terminate at the API Gateway.

The gateway can handle SSL/TLS work such as encryption and decryption before forwarding requests over the internal network. This local lesson uses HTTP so it can focus on routing without certificate setup.

1

API Gateway

Owns the external entry point, selects a service, and can centralize authentication, rate limiting, TLS termination, and API policies.

2

Load Balancer

Exists only on the scaled Catalog path and distributes Product requests between its healthy replicas.

3

Application Services

Focus on business logic while infrastructure components handle external routing and traffic distribution.

In our setup

Nginx performs both infrastructure roles.

The API Gateway routes User and Order directly to one service instance each. Product requests go through a separate L7 Catalog Load Balancer, which uses round robin across two Catalog Service instances.

What this gives us

  • One stable public API address
  • Independent scaling per service
  • No unnecessary Load Balancers
  • Catalog traffic distributed across replicas
  • Clear separation between service and instance selection

What still remains

  • The single API Gateway remains a Single Point of Failure (SPOF)
  • The Catalog Load Balancer is also one infrastructure instance
  • User and Order still have one application instance each
  • Gateway capacity cannot yet scale horizontally

The next design pressure

How do we remove the API Gateway SPOF?

Run multiple API Gateway instances and place an Edge/L4 Load Balancer above them.
