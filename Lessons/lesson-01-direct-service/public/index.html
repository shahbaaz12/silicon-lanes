What this teaches

Simple to start. Harder to scale.

Suppose you create a simple server and host it on the internet.

A client can interact with your service using its hostname or IP address, and the incoming requests are handled directly by your server.

This is a simple and fast setup, but it puts more responsibility on the server. Along with your application’s business logic, the server may also handle tasks such as:

  • SSL/TLS termination
  • Encryption and decryption
  • Compression and decompression
  • Connection handling

For low traffic, this usually isn't a problem. Even a standard server can comfortably handle hundreds of requests depending on the workload.

However, this setup has a few drawbacks:

  • Single Point of Failure (SPOF): If the server goes down, the entire application becomes unavailable.
  • Limited scalability: One server can only handle a certain amount of traffic.
  • No load distribution: All incoming requests are handled by the same machine.
  • More server overhead: Infrastructure-related tasks consume resources that could otherwise be used for business logic.

So while this setup works well for small applications, it becomes harder to scale and maintain as traffic grows.
