What this teaches

Use one entry point for many services.

The next step is understanding an API Gateway.

The flow becomes:

Client→API Gateway→Appropriate Service

An API Gateway sits in front of your backend services and acts as a single entry point for client requests. It examines each request and routes it to the correct service.

Think of it like a shopkeeper.

You tell the shopkeeper what you need, and instead of finding the right place yourself, the shopkeeper gets it for you.

Why is this useful?

As an application grows, it may contain multiple services such as User Service, Order Service, Payment Service, and Notification Service.

Without an API Gateway, the client may need to know the address of every service. With a gateway, the client only needs to know one endpoint:

Client→API Gateway→User / Order / Payment Service

An API Gateway can also handle common concerns such as:

  • Authentication and authorization
  • Rate limiting
  • Request routing
  • Request and response transformation
  • Logging and monitoring
  • API versioning

API Gateway vs Load Balancer

They solve different problems.

Load Balancer

  • Distributes traffic between multiple instances of the same service.
  • Mainly improves scalability and availability.

API Gateway

  • Routes requests between different services and APIs.
  • Adds API-level features such as authentication, rate limiting, and routing rules.

They are often used together, not as replacements for each other.

Client→API Gateway→Load Balancer→Service Instances

The API Gateway decides which service should handle the request, while the load balancer decides which instance of that service should handle it.

In our setup

We use Nginx as a simple API Gateway. It reads the HTTP path and routes the request to one of six services: User, Catalog, Inventory, Cart, Order, or Payment.

The client knows only the gateway address. Rules such as /api/users and /api/products decide which private service receives the request.
