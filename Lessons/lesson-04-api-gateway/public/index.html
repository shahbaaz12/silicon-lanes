What this teaches

Use one entry point for many services.

An API Gateway sits in front of backend services and acts as a single entry point for client requests. It examines the request and routes it to the correct service.

Client→API Gateway→Appropriate Service

A useful analogy

Think of the gateway like a shopkeeper.

You tell the shopkeeper what you need. Instead of knowing where every item is stored, the shopkeeper interprets your request and gets it from the right place.

Without an API Gateway, the client may need to know the address of every service. With a gateway, the client knows one endpoint while paths such as /api/users, /api/products, and /api/orders select the appropriate backend.

Common gateway responsibilities

  • Authentication and authorization
  • Rate limiting
  • Request routing
  • Request and response transformation
  • Logging and monitoring
  • API versioning

In our setup

Nginx is a deliberately simple API Gateway.

It reads the HTTP path and routes to one of six services: User, Catalog, Inventory, Cart, Order, or Payment. The client never needs their individual addresses.

Different decisions

API Gateway vs Load Balancer

They are often used together, not as replacements for each other.

Load Balancer

Which instance?

Distributes traffic among multiple instances of the same service to improve scalability and availability.

API Gateway

Which service?

Routes requests among different services and APIs, with API-level policies around that routing.

Client→API Gateway→Load Balancer→Service Instance

What this gives us

  • One stable API address for clients
  • Clients are decoupled from service locations
  • Internal service addresses remain hidden
  • Central routing and cross-cutting policies
  • Services can evolve behind the gateway

What still remains

  • The single API Gateway is now a Single Point of Failure (SPOF)
  • Each service has only one instance in this lesson
  • A gateway route does not distribute load among service replicas
  • Gateway capacity and availability must eventually scale too

The next design pressure

Should every service scale in the same way?

Some services receive more traffic than others. The next lesson adds a Load Balancer only where multiple replicas are needed.
